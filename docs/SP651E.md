# 灯带 / SP651E 预适配

## 当前交付边界

Android 中设备名固定为「灯带」。SP651E 按单路 PWM 单色灯带控制器准备，只提供开关、1–100% 亮度，不展示 RGB、色温、流水或音乐控件。

服务端已实现无需原厂 App、无需米家绑定的直接 BLE 驱动。当前确认的实物固件为 **V3020.07**，米家二维码标识为 `sperll.light.sglw`，产品 ID 为 14705；实际控制使用名为 `SP651E` 的另一条 BLE 广播，而不是米家 FE95 广播。公开示例只保留占位地址，不记录用户真实 MAC。

已在仅给控制器供电、未接灯带的条件下，验证状态查询、电源切换、常亮模式和两档亮度写入，并读回参数确认、还原原值。这确认了控制器协议，不代表已经验证实际灯带亮度、PWM 波形、供电功率或升压器稳定性。其他固件和灯具类型默认拒绝控制，必须另外验证。

产品资料：[SP651E 单色 PWM 控制器](https://suntechlite.com/sp651e-1ch-pwm-single-color-led-controller/)。该页面可用于核对硬件类别，不作为字节协议依据。

### 默认安全行为

- 旧配置不需要新增字段；灯带默认未配置，不影响风扇、台灯、传感器、充电器和 W96D。
- 默认未配置时不启动额外 BLE 活动；启用后复用原有共享扫描器、事件循环和 GATT 协调锁，仅在建立连接和订阅时占用设置锁，随后恢复扫描并保留 GATT 会话。后台每 8 秒查询并接受设备通知，HTTP GET 只读取状态快照，不排队重连；超过 20 秒的状态或失败的查询不会标为在线。服务端不主动开灯，不改变电扇恢复设置；控制器自身断电恢复行为取决于其已有固件设置，本次未修改。
- 未配置/停用时 GET 返回明确状态和未知电源值，而不是伪装在线或已关灯；PATCH 返回 503。
- 只有明确选择 `banlanx-sp651e` 并使用 coordinated 启动器才接入真实驱动；未知协议仍为 `protocol_pending`，PATCH 返回 501。固件不匹配、设备离线或操作超时都不会回显成功。
- 控制完成必须重新读到与命令一致的设备状态，否则返回 503。亮度调整会切换到单色常亮模式并保持原开关状态，因为实测音乐模式会忽略亮度指令。不会顺便改动通电恢复、遥控绑定、定时或固件。
- 新客户端连接旧服务端时，灯带页显示「路由器尚未安装灯带模块」；其他设备不受影响。

## 服务端配置

放在路由器本地 `/lotusemmc/lanmihome/config.json` 顶层，或 `devices.light_strip`；顶层配置优先：

```json
{
  "light_strip": {
    "enabled": false,
    "model": "SP651E",
    "protocol": "banlanx-sp651e",
    "address": ""
  }
}
```

接入时填入广播名称为 `SP651E` 的控制器 MAC，并将 `enabled` 改为 `true`，不要填写米家广播的另一条地址。现有安装器会安装 `light_strip.py` 和 `sp651e.py`，保留现有 `config.json`（包括 `recovery.enabled=false`），不会主动启用灯带。不需要安装或绑定米家/BanlanX，不需要账号密码、miIO token、云服务或额外蓝牙适配器。

## API 合约

`GET /api/v1/light-strip`

```json
{
  "name": "灯带",
  "model": "SP651E",
  "address": null,
  "enabled": false,
  "available": false,
  "control_ready": false,
  "power": null,
  "brightness": null,
  "status": "not_configured",
  "setup_required": true,
  "error": null,
  "capabilities": {
    "model": "SP651E",
    "enabled": false,
    "protocol_ready": false,
    "protocol": "banlanx-sp651e",
    "controls": ["power", "brightness"],
    "brightness_min": 1,
    "brightness_max": 100
  }
}
```

`PATCH /api/v1/light-strip` 接受 `{"power":true}`、`{"brightness":35}` 或同时设置两项。`power` 必须是 JSON 布尔值；`brightness` 必须是 1–100 整数。空对象、字符串、浮点、布尔亮度、RGB、色温等字段返回 400，且不发送部分命令。

状态：`not_configured`（未配置）、`disabled`（停用）、`protocol_pending`（驱动未验证）、`offline`（驱动读取失败）、`ready`（读到实际设备状态）。`/api/v1/state` 和 `/api/v1/capabilities` 包含对应灯带信息。客户端附加识别旧服务端和路由器连接错误。

## 实物接入与后续验证

1. 控制器正反面型号、参数标签和说明书照片，确认确实是 SP651E，不是 SP631E / SP652E 等近似型号；提供灯带、电源额定电压及灯带总功率。按厂商要求使用匹配的低压直流电源，不接市电到控制器 DC 端。
2. 不需要原厂 App。控制器铭牌允许 5–24V DC，先用合适的低压直流电源只给控制器供电，即可由路由器发现广播、识别固件和查询状态。5V 给控制器供电不意味着可以直接驱动额定 12V/24V 的灯带。
3. 已确认服务 UUID 为 FFE0，特征 FFE1 支持 write / write-without-response / notify。当前固件支持未配对直接连接；不调用 pair、不上传凭据、不做 OTA，不尝试改变米家认证特征。
4. 核对新固件时，先使用状态查询验证帧头、长度、固件和单通道灯具类型，绝不因 UUID 相同就自动兼容。对尚未验证的固件，保持禁用并仅采集必要的非敏感协议样本。
5. 升压器和灯带接齐之后，再确认真实开关、1%/25%/50%/100% 亮度、离线恢复、与 W96D/充电器共存，以及控制器断电恢复设置是否符合需求。协议参数读回不能替代这些电气/照明实测。

## 本地验证

```sh
python -m pip install -r router/requirements-test.txt
python -m unittest discover -s router/tests -v
PYTHONPATH=tools/cuktech_ble_probe/src python -m unittest discover -s tools/cuktech_ble_probe/tests -v
gradle --no-daemon :app:assembleDebug
```

自动化测试使用实物状态帧及注入的假 transport 验证协议、校验、模式处理和锁释放，不会模拟在线状态给生产客户端。Android 构建需要项目要求的 SDK 36 和匹配的 Gradle/JDK。开发源码未提交/推送前，GitHub 安装器仍下载已发布的旧代码，不能用它获取本地这次改动。

测试依赖固定了包含现有 `miio.integrations.genericmiot` 导入路径的 python-miio 开发版本；PyPI 的旧版 0.5.12 不具备该路径。不要因本地运行测试而替换路由器上已验证的依赖。

GitHub Actions 在 APK 构建前运行灯带/HTTP/协议测试及既有 CUKTECH 测试，再安装 SDK 36 并构建 Android 客户端；本机未配置 Android SDK 时使用 Actions 构建。构建 APK 不会部署到路由器或改变其真实设备配置。
