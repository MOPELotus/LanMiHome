# 灯带 / SP651E 预适配

## 当前交付边界

Android 中设备名固定为「灯带」。SP651E 按单路 PWM 单色灯带控制器准备，只提供开关、1–100% 亮度，不展示 RGB、色温、流水或音乐控件。

本次完成服务端接口、客户端入口、状态解析、控制 UI、安装器集成和无硬件测试。**尚未实现或验证 SP651E 的实际通信驱动**。不能把「支持米家 / BanlanX」理解为已有风扇的 MIoT LAN、普通 BLE GATT、BLE Mesh 或 SP631E 协议可以直接复用。没有实物、广播、GATT 和必要的鉴权信息前，不猜 UUID、字节命令或凭据。

产品资料：[SP651E 单色 PWM 控制器](https://suntechlite.com/sp651e-1ch-pwm-single-color-led-controller/)。该页面可用于核对硬件类别，不作为字节协议依据。

### 默认安全行为

- 旧配置不需要新增字段；灯带默认未配置，不影响风扇、台灯、传感器、充电器和 W96D。
- 不启动额外 BLE 扫描、连接、重试或自动开灯；不改变现有蓝牙协调和电扇恢复设置。
- 未配置/停用时 GET 返回明确状态和未知电源值，而不是伪装在线或已关灯；PATCH 返回 503。
- 即使填写地址并开启配置，没有实物验证驱动仍为 `protocol_pending`，PATCH 返回 501。**仅修改配置无法完成实际控制。**
- 以后接入 transport 时，控制完成必须重新读到与命令一致的设备状态，否则返回 503，不乐观回显成功。调节亮度不额外发送开灯命令。
- 新客户端连接旧服务端时，灯带页显示「路由器尚未安装灯带模块」；其他设备不受影响。

## 服务端配置

放在路由器本地 `/lotusemmc/lanmihome/config.json` 顶层，或 `devices.light_strip`；顶层配置优先：

```json
{
  "light_strip": {
    "enabled": false,
    "model": "SP651E",
    "address": ""
  }
}
```

到货之前保持以上状态。现有安装器会安装 `light_strip.py`，保留现有 `config.json`（包括 `recovery.enabled=false`），不会主动启用灯带。

## API 合约

`GET /api/v1/light-strip`

```json
{
  "name": "灯带",
  "model": "SP651E",
  "address": null,
  "enabled": false,
  "available": false,
  "control_ready": false,
  "power": null,
  "brightness": null,
  "status": "not_configured",
  "setup_required": true,
  "error": null,
  "capabilities": {
    "model": "SP651E",
    "enabled": false,
    "protocol_ready": false,
    "controls": ["power", "brightness"],
    "brightness_min": 1,
    "brightness_max": 100
  }
}
```

`PATCH /api/v1/light-strip` 接受 `{"power":true}`、`{"brightness":35}` 或同时设置两项。`power` 必须是 JSON 布尔值；`brightness` 必须是 1–100 整数。空对象、字符串、浮点、布尔亮度、RGB、色温等字段返回 400，且不发送部分命令。

状态：`not_configured`（未配置）、`disabled`（停用）、`protocol_pending`（驱动未验证）、`offline`（驱动读取失败）、`ready`（读到实际设备状态）。`/api/v1/state` 和 `/api/v1/capabilities` 包含对应灯带信息。客户端附加识别旧服务端和路由器连接错误。

## 到货后需要提供 / 设置什么

1. 控制器正反面型号、参数标签和说明书照片，确认确实是 SP651E，不是 SP631E / SP652E 等近似型号；提供灯带、电源额定电压及灯带总功率。按厂商要求使用匹配的低压直流电源，不接市电到控制器 DC 端。
2. 原厂 App（米家或 BanlanX）的设备信息、固件版本和可用功能截图；先确认原厂 App 可正常开关、调光。不要为了准备接入反复恢复出厂或随意更换绑定方式。
3. 蓝牙广播名称、MAC 地址、广播服务 UUID / 厂商数据、GATT 服务与特征列表（注明 read/write/notify）；如扫描看不到设备，先退出手机 App 释放连接再测。可在设备到货后由路由器侧协助采集。
4. 如公开资料不能确认协议，提供原厂 App 开/关、10%/50%/100% 调光的脱敏 HCI 交互，用于验证特征、命令和状态通知。包含鉴权材料的日志应私下交付，不上传公开仓库。先判断是普通 BLE、标准认证还是 Mesh，再确定是否需要授权凭据或兼容网关；目前不要求小米账号密码、Wi-Fi 密码，也不假定一定存在 miIO token。
5. 确认协议后补齐真实 transport，并接入现有 BLE/GATT 协调机制，避免与充电器、W96D 抢占扫描/连接。再填写地址、开启配置，并完成设备离线重试、重启后不自动开灯和与原设备共存的实测。

## 本地验证

```sh
python -m pip install -r router/requirements-test.txt
python -m unittest discover -s router/tests -v
PYTHONPATH=tools/cuktech_ble_probe/src python -m unittest discover -s tools/cuktech_ble_probe/tests -v
gradle --no-daemon :app:assembleDebug
```

协议适配器测试使用注入的假 transport 验证服务端合约，不是模拟设备在线给生产客户端使用，也不代表实际 SP651E 已可控。Android 构建需要项目要求的 SDK 36 和匹配的 Gradle/JDK。开发源码未提交/推送前，GitHub 安装器仍下载已发布的旧代码，不能用它获取本地这次改动。

测试依赖固定了包含现有 `miio.integrations.genericmiot` 导入路径的 python-miio 开发版本；PyPI 的旧版 0.5.12 不具备该路径。不要因本地运行测试而替换路由器上已验证的依赖。

本地验证包括 25 项灯带/HTTP 测试及 15 项既有 CUKTECH 测试。GitHub Actions 在 APK 构建前运行以上测试，再安装 SDK 36 并构建 Android 客户端；本机未配置 Android SDK 时使用 Actions 构建。构建 APK 不会部署到路由器或改变其真实设备配置。
